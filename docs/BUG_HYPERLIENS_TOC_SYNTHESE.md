# Summary: Table of Contents Extraction Bug in .docx

Synthesis document of the problem encountered during test run 7: the TOC of a contract was visible in Word but ignored by the agent Phase A. Covers symptom, initial false diagnosis, real root cause, solution adopted, and lessons learned.

## 1. Symptom

During test run 7:

- The agent completed Phase A concluding `toc_status = "not_found"`,
- The report indicated no table of contents was detected
- Yet visually in Word, the TOC was clearly present at the start (Summary / Table of Contents with ~70 entries)

Alert raised:

> I think the index doesn't appear clearly even though for me it's displayed, maybe it's an image in Word or something like that

## 2. Initial (False) Diagnosis

First hypothesis: "Phase A is doing its job, but the text of shred 1 genuinely doesn't contain the TOC, so the LLM is right to find nothing."

Inspection of the `contract_basic_shreds.json` from test run 7: confirmed, TOC was absent from extracted text. So we looked at the shredder.

Second hypothesis: "The .docx contains a TOC image, not text."

Inspection of the `.docx` archive as ZIP:

- No significant image files in `word/media/`
- But in `word/document.xml` presence of a dynamic Word field:

```xml
<w:sdt>
  <w:sdtContent>
    <w:p>
      <w:fldChar w:fldCharType="begin"/>
      <w:instrText> TOC \o "1-3" \h \z \u </w:instrText>
      <w:fldChar w:fldCharType="separate"/>
    </w:p>
    <w:p>
      <w:hyperlink w:anchor="_Toc...">
        <w:r><w:t>1. Definitions ........... 5</w:t></w:r>
      </w:hyperlink>
    </w:p>
    ...
  </w:sdtContent>
</w:sdt>
```

The TOC is not an image and not absent: it's dynamically generated by Word via a TOC field wrapped in a **Structured Document Tag** (`<w:sdt>`), and each entry is a **hyperlink** toward the corresponding clause anchor.

## 3. Why Python-docx Didn't See It

The agent used `python-docx` for text extraction:

```python
from docx import Document
doc = Document(file_path)
for p in doc.paragraphs:
    ...
```

Two `python-docx` limitations combined explain invisibility:

1. **`<w:sdt>` containers ignored**. Paragraphs inside an `<w:sdt>` are not exposed by `doc.paragraphs`. Modern Word dynamic TOCs are systematically encapsulated in `<w:sdt>` to enable "Update TOC" actions.
2. **Hyperlink text ignored**. Even when a paragraph is exposed, `paragraph.text` only concatenates direct runs (`<w:r>`); runs nested in a `<w:hyperlink>` are skipped by default.

First fix attempt (collect runs under `<w:hyperlink>` in paragraph.text): **failed**. Cause: paragraphs in question aren't in `doc.paragraphs` at all, the problem is upstream.

## 4. Solution Adopted

Complete bypass of `python-docx` for text extraction. Parse raw XML from `word/document.xml`, descend recursively into `<w:sdt>`, and collect all `<w:t>` encountered by traversing the tree with `iter()`, which also picks up hyperlink text.

Summary of new extraction strategy:

- Open `.docx` as a zip archive
- Load `word/document.xml` with `xml.etree.ElementTree`
- Visit `<w:body>` in depth
- For each `<w:p>`: concatenate text of all descendant `<w:t>`, replace `<w:tab/>` with `\t`, `<w:br/>` with `\n`
- For each `<w:tbl>`: descend cell by cell, aggregate into rows
- For each `<w:sdt>`: descend into `<w:sdtContent>` (the key fix)
- For other containers (sectPr, etc.): defensive recursive descent in case text is hidden

The `[PARAGRAPH N]` and `[TABLE N ROW M]` marker is preserved in output to remain compatible with downstream shredder.

`python-docx` remains declared as a dependency (via `require_module`) to quickly detect a broken Python environment, but is no longer called directly.

Complete function code is in `docs/TOOL_SHRED_DOCX.md`.

## 5. Result

After patch, on a .docx containing dynamic TOC:

- Each TOC entry appears in extracted text, prefixed by `[PARAGRAPH N]`, with its number, title, and page number
- Phase A finds TOC, accumulates it shred after shred, marks it `complete` when the contract body begins

No regression on .docx **without** dynamic TOC: the XML tree contains no `<w:sdt>`, parser simply visits `<w:p>` and `<w:tbl>` as before.

## 6. Lessons Learned

- When a binary/structured format (docx, pptx, xlsx) "loses" text visible to the eye, suspect format-managed containers first (sdt, fields, comments, smartArt) before concluding "it's not in the file".
- High-level wrappers (`python-docx`) have documented blind spots. For "extract everything visible", parsing XML directly is more reliable.
- Always separate "the shred has no TOC" (contract/LLM-side problem) from "the extractor didn't see TOC" (shredder-side problem). A single `print` of extracted text from shred 1 would have saved time.
